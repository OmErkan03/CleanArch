## Intent
The project has no automated tests, so no behavior is proven and every later spec has nowhere to
put its evidence (AGENTS.md rule 4). The developers want a working test foundation: unit tests
that run in the fast inner loop and integration tests that run the real API against real
PostgreSQL and Redis in the full profile, both wired into `./scripts/check` as
`docs/testing.md` describes. Success: a later spec can add a unit or an integration test without
touching build or check configuration, and a failing test turns check red. Deliberately not done:
covering the existing business rules BR-1…BR-19 (later specs and backlog), architecture tests
(B-4), replacing `DateTime.UtcNow` (B-3), and any change to production behavior.

## Requirements
- R-1: There is a unit test suite that needs no container runtime and no network, and runs in both
  check profiles.
- R-2: There is an integration test suite that exercises the API through HTTP against a real
  PostgreSQL 17 and a real Redis 7 created for the test run; it runs in the full profile only.
- R-3: Whether a test is an integration test is decided by a marker on the test (selector), not by
  a list of projects or files in check configuration; every test runs in exactly one of the two
  test steps.
- R-4: Each suite ships with one starter test that proves real, existing behavior, so the suite is
  known to run and report real results.
- R-5: A test run starts from a known state and leaves nothing behind: no databases, containers or
  processes survive the run, and the developer's local `docker-compose` data is never touched.
  The application under test runs in a dedicated `Testing` environment: its signing key is
  generated by the test code per run and its connections point at the test containers.
- R-6: A machine that cannot run integration tests is told so before any step runs — the full
  profile fails with the missing prerequisite named; it is never skipped silently.
- R-7: Production behavior does not change. Any change to production code is limited to what the
  test host needs to start the application and is behavior-neutral.

## User experience
none — no user interface. The "users" are developers and agents running `./scripts/check`.

## Constraints & out of scope
- Tooling decided at bootstrap (`docs/testing.md`): xUnit v3, Shouldly, `WebApplicationFactory`,
  Testcontainers; test projects under `ECommerce/tests/`, in `UludagEnerji.slnx`.
- New packages follow `docs/security.md` "Dependencies" (named in the plan, approved at plan gate).
- Integration tests use their own connection settings; they never read the secrets in tracked
  `appsettings*.json` as their source of truth (B-1).
- Containers: one PostgreSQL and one Redis per test run, shared by all integration tests of that
  run (per-test isolation is for later specs). Budget: the integration step takes ≤ ~2 minutes
  on the development machine.
- Deliberate breaks used as evidence (AC-6, AC-8) are temporary and never committed; the
  evidence is the recorded observation in the plan's evidence table.
- Sensitive area: none — no production behavior changes (R-7). The starter integration test only
  observes existing auth behavior.
- Out of scope: tests for BR-1…BR-19 beyond the two starter tests; architecture tests (B-4);
  `TimeProvider` (B-3); SDK pinning (B-2); code coverage reporting; CI changes beyond what is
  needed for check to run the new steps.

## Acceptance criteria
- [x] AC-1 — `./scripts/check --fast` runs the unit tests and reports a test count greater than zero; it starts no container.
- [x] AC-2 — `./scripts/check` (full) runs the unit tests and the integration tests; each step reports a test count greater than zero.
- [x] AC-3 — Starter unit test: creating `Money` with a negative amount is rejected and with zero is accepted (BR-19).
- [x] AC-4 — Starter integration test: an anonymous `GET /api/products` against the app running on real PostgreSQL and Redis containers returns 401 with a ProblemDetails body (BR-1).
- [x] AC-5 — A test marked as integration runs only in the full profile; an unmarked test runs in both; a newly added test in either project is picked up without editing `scripts/check.conf`.
- [x] AC-6 — A deliberately failing unit test makes both profiles red; a deliberately failing integration test makes the full profile red and leaves the fast profile green.
- [x] AC-7 — After each profile the residue test is clean (`./scripts/residue`, `./scripts/residue --fast`), and no test container remains (`docker ps -a` shows none from the run).
- [x] AC-8 — With no container runtime available, `./scripts/check` fails before the first step naming the unmet integration prerequisite, while `./scripts/check --fast` still runs green (simulated with `DOCKER_HOST=tcp://127.0.0.1:1`).
